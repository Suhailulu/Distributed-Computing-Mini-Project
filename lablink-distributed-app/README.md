# LabLink: Distributed Campus Lab Resource & Queue Coordinator

**Course:** CS3551 – Distributed Computing  
**Register number:** 814724104152

LabLink is a mini-project prototype for coordinating shared college laboratory resources across multiple clients. It demonstrates resource reservations, conflict prevention, idempotent retries, a waiting queue, cancellation, and an event log.

## Features

- Responsive web dashboard
- REST API built with FastAPI
- SQLite persistent storage
- Default sample resources added automatically
- Reservation conflict checking for exclusive resources
- Request IDs to make retries idempotent
- Waiting queue when a resource slot is occupied
- Cancellation and queue promotion
- Event log for key decisions
- API documentation generated by FastAPI

## Run locally

### Windows (PowerShell)

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
uvicorn app:app --reload
```

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn app:app --reload
```

Open `http://127.0.0.1:8000` in your browser.

API docs: `http://127.0.0.1:8000/docs`  
Health check: `http://127.0.0.1:8000/api/health`

The SQLite database `lablink.db` is created automatically on first launch. It is excluded from Git because it is runtime data.

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Service health |
| GET | `/api/resources` | List resources |
| POST | `/api/resources` | Add a resource |
| GET | `/api/reservations` | List reservations |
| POST | `/api/reservations` | Request a reservation |
| POST | `/api/reservations/{id}/cancel` | Cancel a reservation |
| GET | `/api/queue` | List waiting requests |
| GET | `/api/events?limit=100` | Read recent event log |

### Example reservation request

Use `POST /api/reservations` with JSON:

```json
{
  "request_id": "demo-request-001",
  "user_id": "student-152",
  "resource_id": "GPU-01",
  "start_time": "2026-10-22T10:00:00+05:30",
  "end_time": "2026-10-22T11:00:00+05:30"
}
```

The start and end timestamps must include a timezone. Reuse the same `request_id` when retrying the same logical request.

## Distributed-computing concepts demonstrated

- **Scalability:** stateless API layer can be replicated; popular resources and database writes can become bottlenecks.
- **Communication:** clients use request-response HTTP calls; a lost response can leave the client uncertain.
- **Failure handling:** stored request decisions support safe retries; event logs support diagnosis.
- **Resource sharing:** an atomic database write and conflict check prevent overlapping confirmed reservations in this single-host implementation.
- **Consistency trade-off:** a production multi-node version would need robust leader election/consensus and a shared durable database.

## Important limitations

This is an educational prototype, not a production-ready distributed cluster. It runs as one application process using SQLite. The standby coordinator described in the report is an architectural extension, not implemented by this code. SQLite write serialization is suitable for a local demo but is not a substitute for distributed consensus. Resource `capacity` is currently descriptive; the implementation treats each resource as exclusive.

Before submission, run the app, test simultaneous overlapping requests, capture screenshots, and report the actual observed output.
